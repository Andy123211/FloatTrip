# 途见 · FloatTrip

途见是一个对话式旅行规划项目：用 Agent 理解需求，以真实地点数据和约束求解编排行程，再通过对话或手动编辑持续调整。它的目标是让旅行规划成为可以查看依据、补充条件和修改结果的过程。

[返回项目首页](../README.md) · [界面展示](../README.md#screenshots) · [快速开始](../README.md#quick-start)

## 从想法到可编辑的行程

用户先描述目的地、日期和偏好。主 Agent 通过对话补齐条件，维护 Planning Brief，并在需求确认后调用规划工具。需要额外信息时，界面提供补充信息卡片，用户回复后继续任务。

完成的行程与对话保留在同一工作区：桌面端并排展示对话、逐日路线和地图，窄屏端通过视图切换查看。用户可以用 `@` 明确引用已保存的行程，提出“第二天轻松一点”等修改，也可以直接调整地点、时段和顺序。

编辑草稿支持跨日切换、撤销和重做；保存时由服务端重算距离。地图、地点照片等外部资源不可用时展示降级状态，不把示意视图当作真实地图结果。

## 当前架构：对话决策与排程分工

默认 `CHAT_AGENT_MODE=react` 使用 ReAct 主 Agent。它维护对话上下文，调用旅行记忆、当前简报和历史行程工具，并通过受控工具执行新规划或修改。

| 环节 | 责任与边界 |
| --- | --- |
| 主 Agent | 理解需求、澄清信息、维护简报、调用工具并解释结果。工具不是独立 Agent。 |
| 天气与 POI | 查询外部数据，为候选地点提供来源；来源真实不代表所有开放、预约信息都完整。 |
| Candidate Builder | 模型补充候选语义，服务端绑定真实 POI 并过滤、兜底。 |
| 确定性优化器 | 使用 OR-Tools CP-SAT 等求解逻辑选择景点、排序与排程，不由模型一次性写出最终时间表。 |
| 质量检查 | 独立检查求解结果，允许有限次候选修复；仍不通过时报错。 |
| 修改子图 | 准备原行程与修改上下文，按需补搜，再由 Planner / Reviewer 调整和评审，随后搜索并推荐餐饮。 |
| Runtime | 管理排队、并发、持久事件、取消、重试和等待用户回复。 |

默认新规划执行链为：

**天气 → 高德景点搜索 → 候选生成 → 确定性优化 → 质量检查 → 保存行程。**

修改流程保留 Planner / Reviewer 循环，并可因疑虑请求用户补充。达到轮数上限后继续收敛并不表示 Reviewer 已通过。餐饮搜索与推荐属于修改图，不是默认新规划的固定步骤；行程保存后还可异步补充游玩贴士。

旧版“Planner ⇄ Reviewer → Time Check”不是当前新规划拓扑。Time Check 函数虽仍在代码中，但未接入当前两张图。架构简图见 [README 工作原理](../README.md#architecture)。

## 记忆可以延续，也可以撤回

旅行记忆保留偏好、约束和来源，用于后续需求理解。用户可以查看、编辑或忘记条目，并为本次旅行表达不同选择；当前明确需求优先于历史画像。

长期记忆提取与会话上下文是不同职责：会话摘要帮助控制上下文长度，长期记忆需要管理来源、作用范围与用户确认。它们都不应被描述为对用户偏好的永久推断。

## 持久化的边界

Run 状态和事件可持久化，SSE 支持断线后的事件回放；取消、重试、等待补充和恢复有对应运行时协议。

默认 ReAct 路径的规划与修改工具在当前 Chat Run 内执行，不自动为每次工具调用创建独立子 Run。主图接入 SQLite checkpointer，工具内部构建的子图没有显式传入 checkpointer，因此不能宣称任意子节点都能独立恢复。系统另有注册到调度器的独立规划 / 修改 Worker 路径。

当前面向单节点部署。详见 [Agent Runtime](agent-runtime.md)。

## 如何理解质量与实验

真实 POI、候选约束和独立检查能帮助发现问题，但不能保证未来的天气、交通、预约或开放情况。界面展示与离线测试通过，也不能替代在线规划质量评估。

仓库保留多代评测工具及实验记录。旧 Planner / Reviewer 评测衡量的是对应链路，不能直接代表当前默认求解流程。新实验应明确冻结的输入、代码版本、调用成本和验收标准，再比较结果。

本文以当前工作区默认 `PLANNING_VARIANT=A` 为基准。B / C 变体及独立面试演示有各自入口与限制，不作为默认能力宣传。
